⚠️ **后果**：玩家**走到"网吧"这一个地点**（`internet_cafe`）时，看不到"上网"这个选择；
`gym` 地点同理。地点与其同名娱乐行动**不通**。

**验证**：
```bash
grep -n "internet_cafe" src/js/data/phase1/actions_extra.js   # 需确认结果（当前为空）
grep -n "internet_bar" src/js/phase1/actions_extra.js
```
（注意路径应为 `src/js/phase1/actions_extra.js`）

**缺口 B —— 娱乐无重复递减，可无限刷**

全库检索 `_entertain` / `递减` / `_visitCount` / `_repeat` 于 `actions_extra.js` 与 `actions.js`
→ **无命中**。即：`ktv` 可以无限次刷 **+25 心情**。

对照《大多数》的娱乐设计律（**同一娱乐 +10 / +5 / +1 三段递减**）：
我们缺这一层 → **心情系统的实际约束力被无限刷削弱**。

**建议动作**：
1. 给 `internet_cafe` / `gym` 两个地点补上**指向同名娱乐行动**的映射（或把地点 action 列表补进去）——
   **成本极低，纯数据**。
2. 给娱乐类行动加"当日重复递减"计数器（对齐《大多数》）：
   第 1 次全额 → 第 2 次 50% → 第 3 次 10% → 之后 0，按天重置。

**平衡风险**：
- 缺口 A 修复：**无**（只是让已有行动可达，不新增数值）
- 缺口 B 递减：⚠️ **中**（会降低心情恢复效率 = 变相提高难度）→ 必须 `npm run baseline` 前后对比

**执行顺序建议**：先修 A（零风险），观察 baseline 无变化后再做 B。

### §7.2 O-2 · 娱乐恢复要有"三段递减"（防坑 1 的机制层解法）

《大多数》的娱乐设计律：**同一种娱乐反复做，情绪收益 +10 / +5 / +1 递减**。

**现状**：见 §7.1 缺口 B —— 全库无递减计数器。
`ktv` 可无限刷 **+25 心情**（`actions_extra.js:613`），只受现金与 AP 限制。
⚠️ 这意味着：**心情系统的实际约束力被无限刷削弱**。

- 第 1 次全额 → 第 2 次 50% → 第 3 次 10% → 之后 0
- 计数器挂 `state.flags._entertainCooldown`，按天重置

**注意与 §7.1 的关系**：§7.1 缺口 A 是"让已有行动可达"（纯数据，零风险），
本节是"限制可达后的收益效率"（动平衡）。
**先做 A、跑 baseline 确认无变化，再做 B。**

**平衡风险**：⚠️ **中**（降低恢复效率 = 变相提高难度）→ 必须 baseline 对比。

### §7.3 O-3 · 核对上轮新增行动的"收益/AP 比"（防坑 3）—— **已实测，确有缺口**

《荣誉打工人》第三坑：**支线收益为负**。

> 原文：「去送一次外卖，**仅能收获10块钱**，但玩家走过去的时间太久了，营收相较于打工并不划算」

**⚠️ 实测结果：我 2026-09-18 新增的 6 个行动中，4 个没有 `payEstimate`。**

| 行动 | apCost | `payEstimate` | `effectEstimate` | 问题 |
|------|--------|--------------|-----------------|------|
| `gov_benefits_apply` 申请低保 | 15 | `0~800` | 心气-5 | 跨度太大（0 到 800），玩家无法判断值不值 |
| `court_labor_arbitration` 劳动仲裁 | 20 | `0~3000` | 心气+3 | ⚠️ **上限 3000 = 打工数倍**，疑似过强 |
| `job_market_resume` 投简历 | 10 | **无** | 职业机会 | ⚠️ **无收益估算**，UI 无法展示预期 |
| `flea_market_haggle` 淘货砍价 | 15 | `0~420` | 修理XP+3 | 尚可 |
| `veg_market_bargain` 买菜 | 10 | **无** | 饱腹+12 食物满足感+6 | 纯消耗类，无收益正常 |
| `suburb_rest` 郊区静养 | 30 | **无** | 健康+6 心气+8 衣物整洁+5 | 纯恢复类（设计正确） |

**一个真问题（另一个已排除）**：

1. ~~`court_labor_arbitration` 上限 ¥3000 抬高~~ —— **复核后排除** ✅
   读完整实现后确认：该行动有**三重约束** ——
   ① `condition` 要求 `st.flags._wageOwed > 0`（**必须先被真实欠薪**）；
   ② 30 天冷却（`_arbitrationDay`）；
   ③ 追回额 = `owed × (0.6 + random(0, 0.3))`，**上限由欠薪总额决定，不是凭空 3000**。
   且胜率上限 90%（需合同+同事证明+智力 60 才够）。
   **→ 这是"把本该属于你的钱要回来"的追偿机制，不是收入源。设计正确，无需改。**
   （`payEstimate: "0~3000"` 只是描述上限，应改为写实文案，见下）

2. **3 个行动缺 `payEstimate` / 文案不精确**：
   - `job_market_resume`（投简历）：**应补**，属机会类，UI 需要预期
   - `veg_market_bargain`（买菜）：**应补**，属消耗类
   - `suburb_rest`（郊区静养）：恢复类，**可以不补收益**，但
     **必须在 UI 上标明"这是恢复类"** —— 否则玩家按"收益类"评估 → 觉得亏 AP
     （**这正是坑 3 的成因**）
   - `court_labor_arbitration`：`payEstimate` 建议从 `"0~3000"` 改成
     `"追回欠薪的 60~90%"` —— **更准确，也更有叙事感**

**建议动作**（顺序）：
1. 补/改 4 条文案（`job_market_resume` / `veg_market_bargain` / `suburb_rest` / `court_*`）
2. 恢复类行动统一加 UI 标识（可并入 §7.4 称号系统所在的展示层改动）

**平衡风险**：**无**（全部是展示文案，不碰数值）。

### §7.4 G-4 · 称号系统（**成本极低，收益明确**）

《打工生活模拟器》的核心长期目标：**搬砖 → 搬砖王**（2800 点经验，约 30 天）。

**我们的现状**：有技能等级（`physique/intelligence/...`）但**没有"称号"这个可见成就**。

**为什么成本极低**：称号是**纯展示层**，不改任何数值。挂一个由现有技能/里程碑派生的称号表即可。
- 例：搬砖满 N 次 → 「砖王」；技能达某级 → 「老师傅」；还清助学贷款 → 「站稳了」
- 消费端：玩家卡片 / 日报告 / 行动页顶部

**为什么值得做**：它是**唯一的"零风险长期目标"**——不碰平衡、不碰事件触达率，
却能直接回答玩家"我到底在变强吗"。

**平衡风险**：**无**（只读现有数值，不写入）。

### §7.5 G-1 · 地点差异化产出（**我们已完整实现，无需动工**）

《荣誉打工人》的巧妙设计：**同一个动作在不同地点挂不同掉落表**（翻垃圾桶案例，
深圳站出建筑/包装、快递柜出维修/有机…）。

**★ 核实结果：这套机制我们已经有了，而且比它更完整。** 三个证据：

1. **`goods.js` 的地点维度**：每个商品有 `buyLocations` / `sellLocations`
   （`goods.js:17-18` 瓶装水：`buyLocations: [wholesaleMarket, slum, factoryZone]`），
   外加 `seasonal` 季节系数。
2. **食材有专属采购入口 + 地点价差**：`phase1/actions_extra.js:1858` 的 `buy_ingredients`
   行动，描述里直接写明"当前市场价 ×" + 该地点 `priceMod` 计算出的系数 ——
   **同一个食材在不同地点价格不同**，正是 G-1 的模式。
3. **53 个商品全覆盖**：其中 20 个 `isIngredient: true` 的食材（rice/flour/pork/fish…）
   没有 `buyLocations`，**看似不可交易**——但复核发现它们由**烹饪系统**消费
   （`core/cooking.js:23` 白饭 = `{itemId:"rice", amount:1}`），
   且经上述 `buy_ingredients` 采购，**链路完整，不是缺口**。

**→ 结论：G-1 不需要新建，也不建议动。**
唯一可选的微调是加大地点价差（当前 `seasonal` 仅 ±10~30%），
但那属于**平衡调整**，需 baseline 对比，优先级低于 §7 其他项。

> ⚠️ 这里又踩了一次"局部观察下结论"：初版我只看 `goods.js` 的 `buyLocations` 为空，
> 就写下"20 个商品是不可交易的缺口"。**复核烹饪链路后该判断被推翻。** 记入更正 6。

### §7.6 G-2 · 心愿系统（情感层，承接"主题不落空"）

《荣誉打工人》的**心愿**（与 NPC 绑定、完成加心情）是它**最受好评**的设计。
且它是唯一能解决 §7 深层问题（坑 7）的机制——

> 玩家长评原话：「心情一点点波动就要靠逃避工作找娱乐补偿……
> 让打工人前面的'荣誉'二字变得更加刺眼」

**→ 心愿的作用**：把"恢复心情"从**逃避式的消费**（去网吧）
变成**有意义的行动**（陪家人吃顿饭、帮邻居一个忙）。
**这才是"在平凡生活中发现美好"这个主题的机制化表达。**

**我们的基础**：已有 NPC 好感系统，缺"**NPC 主动提要求**"这一环。

**建议动作**：`state.flags._wish` + 每日由 NPC 生成 1 条小愿望（买菜、陪聊、修东西），
完成给"心情 + 好感"——**注意与 O-2 递减规则一致**（避免又变成刷分）。

**平衡风险**：⚠️ 中（新增心情来源）→ 与 O-1/O-2 一起跑 baseline。
**建议排期**：O-1/O-2 之后，因为它依赖前两者的数值框架稳定。
