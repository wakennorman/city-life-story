## §3 新功能类（非缺陷，需产品决策后再开工）

### §3.1 思想气泡（借鉴 OpenRCT2 Guest Thoughts）

- **现状**：数值状态与玩家的沟通仅有零散 `addMessage`（`main.js:4818-4823`，约 30% 概率）。
- **建议**：在 `src/js/ui/render.js:2380 createActionCard()` 按阈值挂载状态提示语。
  示例：疲劳 > 80 → 「你太累了，现在打工只能拿到 60% 的钱」。
- **前置依赖**：§2.1 的归因数据源。**先有归因，才有话可说**——不要先做气泡再造数据。
- **消费方共用**：与 §2.1 的 daily_report 读同一份 `addStatDelta` 数据，不新建数据源。
- **风险**：会显著增加 UI 文本量 → 必须遵守 `memory/全中文UI原则.md`（玩家可见文本纯中文）。

### §3.2 地点邻接加成（借鉴 CubeCity）

- **现状**：`src/js/data/locations.js` 有 24 个地点；`main.js` 打工结算链（`:4532-4752`）**无任何地点相关系数**——地点目前只是菜单分组。
- **建议**：住宅地 ↔ 工作地的通勤 AP 折扣；常去地点 ↔ 对应 NPC 好感增速。
- **⚠️ 风险**：**会改变经济平衡** → 必须跑 `npm run baseline` + `npm run check:balance` 做前后对比。
- **建议做法**：先做 1~2 条，验证玩家能否感知，**不要一次性铺开**。

### §3.3 每日事件保底（先测再定，不要盲改）

- **现状**：`events_core.js` 的 `_pendingEvent` 是单槽 → 一天最多 1 个事件；`:198` 基础率 `0.18 + day*0.0005`（上限 0.35）。
- 修复槽垄断后，随机池投递 82 次 / 400 天 ≈ **20%**。
- **先测**：用 `seed=20260915, 400 天` 复现「零事件日占比」，拿到当前值**再决定**是否需要保底。
- **不要**为了"热闹"盲目提高频率：会稀释事件价值，且 `news_system.js`（29,619 行）已有体量压力。
