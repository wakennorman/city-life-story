如果你的cloud code配置的是第三方API，然后用的时候发现推理变慢，token暴涨，很有可能不是大模型API的问题，而是clock code，在你的每个请求里偷塞了五个随机字符，如果你第三方API没有特殊处理这些字符，则会导致缓存疯狂失效，这期视频教你如何修复这个问题，先看一眼这段字符长什么样，还记得我们之前讲解提示词缓存的，第一期视频里，用cloud tab抓的同一段对话，给clock code连续发，Hello，Fine，thank you吗，然后这次我们就可以使用对比上次这个功能了，比如说我们对比第二个和第一个请求，我们可以看到这个系统提示词的第一个block，就不一样对吧，我们仔细看一下这个c c version，还有这个cc entry point，它是没变的，就是这个CCH，后面这五位16进制字符都变了，第一轮是这个97BD6，然后第二轮变成了24C2D了，我们可以同样看看第三轮，可以看到是不是从24C2D，它变成了EAD88了，这一行就叫x anthropic bilin header，注意它不是htp header，而是作为上下文理被当做系统提示词，最开头的部分发过去的，这里是关键，然后我们把里面的三个字段分别看一下，第一个是cc version，他前面这个2.1.119是coco的版本号，后面这个AF2是一个三位的16进制完整性哈，希然后第二个这个cc entry point，它是告诉服务器端是从哪个入口进来的，这个CLI就是命令行模式。

然后如果用杠P这个参数启动，它会变成SDKCLI，然后这个CCH后面跟着，就是刚才提到了这个五位16进制字符，它是每次都在变的，我们复习一下前面两期讲过的知识点，prompt cash是前缀缓存，服务器端按照tools system，然后messages的顺序拼前缀，具体写几个缓存键，是看请求里的cash control段，你在哪个block上打这个标记，那么服务器端就把从开始一直到这一块结尾，算一个BREAKPOINT，并且写入一个缓存，键值为开头到这个BREAKPOINT所有上下文的哈希值，所以每次请求实际上是打了三个BREAKPOINT，第一个就在这个system的第二个block的末尾，第二个是在system的第三个的末尾，然后第三个是挂在了这个user message的上，但CCH在哪，在system的第一个block排在所有BREAKPOINT的前面，所以它一遍三个BREAKPOINT算出来的哈，希就全部跟着变了，这里一个字符不一样，那么后面三个全部都miss掉，我们抓取的session里面，第一个请求刚把前缀缓存写进服务器端，第二个第三个请求的CCH1换，那么整个前缀哈希就都对不上了，我个人猜测，ANTHROPIC的服务器端会识别这一段请求，头是他自己塞进去的，所以算缓存key的时候会跳过这一段，但是第三方大模型转发服务，他是不知道这个细节的，看到了还以为就是普通的系统提示词，所以每次都拿整个SISTANT数组算哈。

希结果就导致缓存都miss了，这个现象，整个clock code用户从今年2月份开始，就一直在报这个问题了，你看我找了这么多个GITHUB的issues，你看其实都是在报告这个CCH导致的这个，catch miss的问题，所以这么多报告也没看到ANTHROPY有什么回应，因为他们自己的服务器是不受影响的，知道问题在哪了，那这个CCH到底怎么生成的，怎么才能关掉呢，我们直接看源代码，在CLO的源代码里，我们搜这个src constant system，点ts文件，然后打开以后我们搜索这个get attribution headers，这个函数，然后眼尖的朋友一下子看到了诶，这一行是不是就是构造这个bilin headed的地方，对吧，然后我们看一下主要的逻辑，首先第一个就是检查这个is attribution headers，enable的函数，如果返回false，就直接返回空了，继续往下看CCH的逻辑，一行代码在这里会检查一个feature的开关返回真，那么CCH都等于五个零，这里比较奇怪的地方是没有CCH，这个值是怎么计算的，每次只是一个静态的字符串，那么真正的计算逻辑在哪里呢，其实上面这个注释他大方的承认了，真相真正的CCH是这个native HTTP站计算的，在请求发出的最后一刻，会覆盖这个CCH等于五个零，这个HTTP native的这个站，它并不是node自带的，它是clock code，用的是棒，B是node的替代品，同样是跑JS代码。

但是底层是用这个ZIG系统语言写的，比node快很多，而且它还有个特点，能把整个项目编译成一个不依赖node的单文件，可执行程序，cloud code就是这么打包出来的，你下下来一个二进制直接跑，装机是不需要装node的，ANTHROPIC不止用棒，而且还fork1份自己的版本叫做BANTHROPIC，然后在他的这个native HT代码里加了一个文件，叫a test station，点ZIG，他专门就干一件事情，在请求发出之前，把JS生成了这个CCH等于五个零，替换成真的CCH值，用占位符是因为这个content length是不用动的，所以buffer也就不用重新分配了，ZIG层在JS引擎的内存空间之外跑jazz层，拦截fetch或者monkey patch，HTTP都摸不到，所以外面看CCH就像凭空出现一样，每次都不一样，看完源代码，你可能想问，为啥ANTHROPY要搞这么复杂一套，连这个ZIG的native层都用上了，一句话，就是防白嫖co的登陆走的是OOS，拿到是token绑定你的pro或者max，订阅走的是订阅价比，直连API按照token计费要便宜的多，所以有人就会想把这个token从二进制里抠出来，自己写代码，调用API等于拿订阅价跑任意请求，所以服务器端得能识别这个请求，到底是不是真的，clock code发的，不是的话，哪怕coco是对的，也直接拒掉，这里服务器靠的就是CCH，它是由ZIG的native HT p层计算的，所以JS层只有CCH等于五个零占位符。

冒充的程序根本拿不到真值，一发请求就露馅了，不过这套防御机制也不是铁板一块，GITHUB已经有开源项目，比如说这个sub to API了，然后把整套的这个CCH算法，已经全部复刻了一遍，所以也就是说，ANTHROPIC藏在ZC层的这个逻辑，在开源社区早就已经透明了，回到代码里，那个is attribution header enable的函数我们跟进去，然后看到第一句就是检查这个cloud code，attribution header这个环境变量，如果是这个FALY就return false，那么这就很简单了，只要设置好这个环境变量，整个building header就返回空串了，所以解决方案就一句话，只要在cloud点这个settings，点JASON文件的这个ENV段里面，把call code attribution header这个环境变量设成零，然后加完之后你重启qr code就可以再抓一次包，验证这个system box从之前的三个会变成两个，之前的这个bilin header，这一行字符串完全消失了，比如这是我抓的，你看第一行就是CLOCKO的身份提示开始了，所以总结一下，如果你的cloud code配置的是第三方API，然后用的时候发现推理变慢，token暴涨，你可以尝试的用clock tab抓一次包，看看是不是有这个CCH的请求头，如果有的话，那么它就可能是你缓存失效的元凶，你可以尝试设置clock code，attribution headers这个环境变量来解决这个问题。
