# 改进方案（基于 step2 诊断）

## Quick wins（P0，改动小，立刻做）

### 1. 修复临时对象分配
- **针对问题**：问题 2 | 每帧 `new` 创建 Vec2 对象
- **具体修改方案**
  - 文件：`src/engine/PhysicsSystem.cpp`（或其他频繁调用的系统）
  - 改动：将局部 `new Vec2(x, y)` 替换为栈上对象 `Vec2{x, y}`；将函数返回类型改为值传递或 `Vec2&` 参数
  - 使用的 API/库：标准 C++ 栈对象
- **改动量**：小
- **风险等级**：低
- **测试方案**
  - 运行 5 分钟 stress test，用 profiler 观察 GC 次数归零或显著减少
  - 对比修改前后帧率稳定性（标准差减少 >20%）
- **优先顺序**：第 1 个

### 2. 资源加载加缓存
- **针对问题**：问题 4 | 同一纹理每帧重新加载
- **具体修改方案**
  - 文件：`src/resource/TextureManager.cpp`
  - 改动：添加 `std::unordered_map<string, Texture*>` 缓存；`Load()` 先查缓存，存在则返回已有指针
  - 使用的 API/库：标准库容器
- **改动量**：小
- **风险等级**：低（仅影响加载路径，渲染不受影响）
- **测试方案**
  - 通过断点或日志确认第二次加载同一纹理时命中缓存
  - 对比加载时间：第二次应为 0ms
- **优先顺序**：第 2 个

## 本周待办（P1，影响大，值得做）

### 3. 解耦 UI 事件处理线程
- **针对问题**：问题 3 | UI 响应延迟（事件在渲染线程同步处理）
- **具体修改方案**
  - 文件：`src/ui/UISystem.cpp`、`src/core/GameLoop.cpp`
  - 改动：引入独立的事件队列 `std::queue<Event>`，渲染线程只提交事件，UI 线程（或 worker 线程）消费
  - 使用 `std::mutex` + `std::condition_variable` 或更轻量的 lock-free queue
  - 使用的 API/库：C++11 线程库或 moodycamel::ConcurrentQueue
- **改动量**：中
- **风险等级**：中（多线程竞态可能产生死锁，需加锁策略 review）
- **测试方案**
  - 模拟快速点击 100 次，测量响应延迟峰值 <16ms
  - 使用 ThreadSanitizer 检查数据竞争
  - 回归 UI 所有交互功能（按钮、对话框）
- **优先顺序**：第 3 个

### 4. 重构 GameManager 职责分离
- **针对问题**：问题 5 | GameManager 耦合度过高（同时管理实体、输入、网络、存档）
- **具体修改方案**
  - 文件：`src/manager/GameManager.cpp` / `.h`
  - 改动：将实体管理拆出为 `EntitySystem`，输入拆出为 `InputHandler`，存档拆出为 `SaveManager`；GameManager 只负责生命周期协调
  - 使用接口基类 `class ISystem`，GameManager 通过多态调度
  - 修改所有引用 `GameManager::instance().` 的地方，改为各自系统的单例或依赖注入
- **改动量**：中
- **风险等级**：高（影响全局调用链，需细致修改每个引用点）
- **测试方案**
  - 逐个功能回归：创建角色、移动、存档读档、网络连接
  - 对比重构前后代码耦合度（使用 include 图谱），目标：GameManager 头文件包含数减少 50%+
- **优先顺序**：第 4 个（与第 3 个并行）

## 长期规划（P2，大改或次要）

### 5. 引入固定时间步长物理循环
- **针对问题**：问题 1 | 帧率不稳定
- **具体修改方案**
  - 文件：`src/core/GameLoop.cpp`
  - 改动：将物理/逻辑更新与渲染分离，使用固定时间步长 `dt = 1/60`，渲染帧率可浮动但物理更新按固定步长累加
  - 实现 `accumulator` 模式
  - 使用的 API/库：标准 `chrono` 库
- **改动量**：大
- **风险等级**：中（需小心累积误差，以及插值渲染）
- **测试方案**
  - 录制 30 秒帧率 log，对比 FPS 波动曲线，要求 FPS < 60 时物理更新仍维持 60 tick/s
  - 通过录像回放验证玩家跳跃位置在不同帧率下一致
- **优先顺序**：第 5 个

### 6. 引入 ECS 架构（可选）
- **针对问题**：问题 5 的延伸 + 未来扩展性
- **具体修改方案**
  - 整体重构实体、组件、系统关系，使用 `EnTT` 或 `flecs`
  - 文件：`src/ecs/` 新建目录，替换原有 `EntityManager`
- **改动量**：大
- **风险等级**：高（需要重写大部分逻辑，且游戏功能可能中断）
- **测试方案**
  - 逐组件迁移，每个系统独立测试后集成
  - 使用对比测试：相同输入下 ECS 版本与旧版本输出完全一致（save file 二进制对比）
- **优先顺序**：第 6 个（仅当游戏稳定且有性能瓶颈时启动）
